1. The Web API Explosion

Why API service discovery is now a genuine productivity problem
40,000+Endpoints on RapidAPI
~24,000APIs on ProgrammableWeb (pre-shutdown)
6,000+Parameters in Shopify alone
Why this matters
  • API marketplaces host tens of thousands of services across dozens of categories.
  • Developers spend significant time hunting for the right endpoint, not coding business logic.
  • Service descriptions are brief, ambiguous, often inconsistent across providers.
Why classical methods break
  • Keyword search misses semantic intent (diet plan ≠ meal recommendation lexically).
  • Multiple APIs cover overlapping functions — disambiguation is hard.
  • Modern users expect natural-language queries, not Boolean logic.

Input: User natural-language query — e.g. "User diet plan by day"

Corpus: 47,592 API endpoints across 49 categories

Output: Ranked list of top-K most relevant endpoints (with method, parameters, invocation URL)

Metrics: Hit@K (recall) and MRR@K (ranking quality), for K ∈ {5, 10, 20}

Why retrieval, not classification?
  • Open vocabulary — new APIs added daily.
  • Tens of thousands of "labels" — softmax infeasible.
  • Natural fit for embedding-based and lexical retrieval.
Why is it hard?
  • Brief queries, long documents — length asymmetry.
  • Many APIs share similar descriptions across vendors.
  • Hierarchical structure: category → API → endpoint.

3. Three Schools of API Retrieval

From rigid keyword matching to LLM-mediated reasoning
Era 1 — Lexical (1995–2015)

Method: BM25, TF-IDF over WSDL/UDDI descriptions.

Pros: Cheap, transparent.

Cons: Misses synonyms (email vs e-mail).

Robertson & Zaragoza (2009)

Era 2 — Semantic (2018–2023)

Method: Sentence-BERT, DPR, BGE — encode query & doc into a shared vector space.

Pros: Captures meaning beyond surface form.

Cons: Static query encoding; length asymmetry.

Reimers & Gurevych (2019), Karpukhin et al. (2020)

Era 3 — LLM-mediated (2023–today)

Method: GPT-4 / Llama reasons over candidates with multi-step prompting.

Pros: Powerful semantic understanding.

Cons: Slow, expensive, hard to audit.

Li et al. (2025), Achiam et al. (2023)

Open question this work explores: Has Era 3 leapfrogged Era 2, or is the Era 2 retrieval stack — combined with modern reranking — already strong enough to match LLM-mediated discovery without the cost?

Static query embeddings

Query encoded by a frozen model (e.g. Sentence-BERT) and matched against pre-computed corpus vectors.

  • Fast, deterministic, scalable.
  • Short queries map weakly when documents are long.
  • No corpus awareness during encoding.
Dynamic query embeddings

Query is rewritten or expanded by a generative model before embedding (HyDE, query expansion, Q2D).

  • Bridges query–doc length asymmetry.
  • Exploits LLM world knowledge.
  • One LLM call per query — non-zero latency & cost.
HyDE (Gao et al., ACL 2023): generate first, embed later

5. Research Objectives

Four-pronged empirical investigation
RO-1 — Reproducibility

Faithfully replicate Li et al. (2025)'s evaluation protocol on a public RapidAPI proxy dataset, since the paper's data is not released.

RO-2 — Retrieval ceiling

Measure how far pure retrieval — modern dense embedders + lexical fusion — can reach on Hit@K and MRR@K relative to the paper's GPT-4 hierarchical pipeline.

RO-3 — Reranking gain

Use HyDE for query rewriting and a cross-encoder for fine-grained reranking; measure the additional gain on MRR.

RO-4 — Cost vs accuracy trade-off

Quantify dollar-cost and latency per query for each pipeline stage; identify the smallest configuration matching the paper.

Hypothesis: The bulk of the paper's reported gains comes from the retrieval stage — not from LLM hierarchical reasoning. A strong neural retriever + cross-encoder should already match or exceed their GPT-4 numbers on most metrics.

HyDE — dynamic query rewriting
  • Llama-3.3-70B (Groq) generates a 40–80 word hypothetical API doc per query.
  • The fake doc is embedded by BGE-large; that vector is used for retrieval.
  • Bridges query–doc length asymmetry; one Groq call per query.
BGE-reranker-v2-m3 — cross-encoder
  • 568M-parameter XLM-RoBERTa-large.
  • Takes (query, doc) pair; returns relevance score.
  • Full attention between query & document — far stronger than bi-encoder for fine ranking.

Why MRR@20 trails despite Hit@20 leading

When our retriever finds the gold endpoint, the cross-encoder ranks it at position 1–2 — better than the paper's average rank. But on the 10 of 50 queries that retrieval misses, the gold is absent from the top-20 entirely; meanwhile the paper's hierarchical LLM occasionally salvages such cases at ranks 6–20.

→ This is the single missing ingredient that a follow-up Phase 3 (LLM hierarchical fallback over top-100) is designed to recover.

16. Discussion — Why Modern Retrieval Wins

Three structural factors
Why each piece matters:

→

→

→
Top-20
Reason 1 — Embedder vintage matters

The paper's Sentence-BERT (2019) is two generations behind BGE-large (2023). Modern contrastive pretraining over web-scale pairs captures semantic nuance that an LLM hierarchical pipeline can only approximate post-hoc.

Reason 2 — Sparse + dense complementary

BM25 catches API-name keywords precisely; dense embeddings catch semantic synonymy. RRF fuses both without score calibration. The paper compared neither.

Reason 3 — Cross-encoders for ranking

BGE-reranker-v2-m3 sees full query–doc cross-attention. The paper's LLM was being asked to do this work — at orders-of-magnitude higher cost.

Implicit critique of the paper: the gains attributed to "hierarchical reasoning" are partially an artefact of comparing against an obsolete embedding baseline. With a 2023-vintage retrieval stack, much of the LLM-hierarchical machinery becomes redundant for Hit@K.

17. Limitations & Honest Caveats

Five places where reviewers will (rightly) push back
Tiny test set (N = 50)

Each correct query shifts Hit@K by 2%. Confidence intervals are wide. Future work expands to 200–500 queries with multi-seed runs.

Queries are LLM-synthesised

Paraphrases of gold descriptions — possible distributional leak. Real developer queries (StackOverflow, GitHub issues) are needed to validate.

Dataset is a proxy

ToolEnv2404 ≠ paper's exact RapidAPI snapshot. Numbers comparable in relative terms; absolute parity requires the paper's authors to release their data.

MRR@20 still trails

Phase 3 (LLM hierarchical fallback for retrieval-missed queries) was designed but blocked by Groq daily quota during the project window. Architecture & code are complete.

Single-platform study

Only RapidAPI's hierarchical structure is tested. ProgrammableWeb-style flat directories may behave differently — explicitly noted by the paper as future work and inherited as a limitation here.

For RESTful API service discovery, a 2023-vintage retrieval stack — BM25 + BGE-large + RRF fusion + a cross-encoder reranker — already beats the paper's GPT-4-based hierarchical pipeline on five out of six standard metrics, at roughly 50× lower per-query cost. The remaining MRR@20 gap is structurally explainable: it traces to ten queries that retrieval misses entirely.

Phase 3 — LLM hierarchical fallback

Apply paper's 3-level recipe over top-100 candidates with two improvements:

  • Pre-filtered candidates instead of full corpus → 5–10× lower token cost.
  • Learned self-checking: cross-encoder probability replaces the paper's heuristic +20/−10.
Phase 4 + benchmarks
  • Self-consistency (N=3) — aggregate LLM samples, +1–3 MRR points.
  • Realistic query benchmark — scrape StackOverflow / GitHub for 200–500 real developer queries.
